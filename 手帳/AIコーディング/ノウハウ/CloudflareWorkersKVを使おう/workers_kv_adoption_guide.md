# Workers KV 導入ガイド・意思決定記録

## 🎯 結論：Workers KV を使うべき理由

新規プロジェクトや既存システムの改善では、**「リアルタイム性」より「圧倒的なコスト削減」を優先し、KV キャッシュ構成へ移行することが合理的**です。

---

## 📊 導入前後の比較

### ❌ 導入前：従来型アーキテクチャの問題点

```
クライアント → Workers → Firestore/RDS (毎回DB参照)
```

### 発生する問題

1. **🐌 遅延が発生**
	- 毎回 DB にアクセスするため、レスポンスが遅い
	- 特に地理的に離れた DB へのアクセスは顕著
2. **💸 負荷増大**
	- アクセスが集中すると DB への負荷が急増
	- 読み取りコストが接続数に比例して増加
3. **💰 オリジンDB のコスト高**
	- Firestore や RDS への読み取り回数が膨大
	- 料金が従量課金で増え続ける

---

### ✅ 導入後：KV 活用アーキテクチャのメリット

```
クライアント → Workers → Workers KV (エッジキャッシュ)
                    ↓ (キャッシュミス時のみ)
                Firestore/RDS
```

### 得られるメリット

### 1. ⚡ 超高速レスポンス

- **物理的距離を短縮、エッジで即答**
- Workers KV はグローバルに分散配置されたエッジキャッシュ
- ユーザーに最も近いデータセンターから返答（〜10ms 以下）
- DB への往復通信を削減

### 2. 🛡️ DB 負荷・コスト削減

- **読み取りの大半を KV が吸収**
- Firestore/RDS への読み取りリクエストが激減
- 60秒に1回程度しか DB を参照しない（キャッシュミス時のみ）
- 読み取りコストが **接続数ではなくキャッシュ更新頻度に依存**

### 3. 📈 高いスケーラビリティ

- **アクセス急増にも自動対応**
- 急激なトラフィック増加でも Workers KV が捌く
- DB へのアクセス集中を防ぎ、安定稼働を維持

## 🔄 アーキテクチャ変更の詳細

### 変更前（ハイブリッド構成）：SDK 主体

### 構成

```
クライアント
  ├─ 読み出し → SDK 直通（リアルタイム、高コスト）
  │              ↓
  │           Firestore DB
  │
  └─ 書き込み → Workers 経由（整合性）
                 ↓
              Firestore DB
```

### 問題点

- ✅ **メリット**: リアルタイム性 ◎、オフライン対応 ○
- ❌ **デメリット**: 読み取りコスト高 ▲、KV 未活用

**読み取りコスト**: 大（接続数に比例）

---

### 変更後（KV キャッシュ構成）：Workers 一本化

### 構成

```
クライアント
  ├─ 読み出し → Workers → KV キャッシュ（有効：ウォームアップ）
  │              ↓ (キャッシュミス: 60秒に1回)
  │           Firestore DB
  │
  └─ 書き込み → Workers 経由（整合性 & KV 更新）
                 ↓
              Firestore DB
```

### 改善点

- ✅ **メリット**: 読み取りコスト激減 ◎、KV フル活用 ◎
- ⚠️ **デメリット**: リアルタイム性 △（許容範囲）、通信量少し増

**読み取りコスト**: 小（ほぼ定額）

### キャッシュ戦略

- **ポーリング**: 〜10秒遅延
- **キャッシュミス**: 60秒に1回の DB 参照（コストほぼ0）

## 💡 Workers KV とは

### 基本仕様

Workers KV は、Cloudflare Workers 専用の **グローバル分散型 Key-Value ストア** です。

- **超高速読み取り**: エッジロケーションからの応答（〜10ms）
- **結果整合性**: 書き込み後、グローバルに反映されるまで最大60秒
- **大容量対応**: キー数無制限、値は最大 25MB
- **低コスト**: 読み取り 1,000万回/月まで無料、以降も $0.50/1,000万回

### 適した用途

✅ **最適**:  
- 設定情報（メンバーリスト、テーマ設定）  
- 在席状況など準リアルタイムデータ（10秒遅延許容）  
- 頻繁に読まれるが更新頻度が低いデータ

❌ **不向き**:  
- 秒単位の厳密なリアルタイム性が必要なデータ（株価、チャット）  
- トランザクション処理が必要なデータ

## 🛠️ 実装パターン

### パターン 1: 読み取り専用キャッシュ

最もシンプルで効果的なパターンです。

```jsx
// Workers 側
export default {
  async fetch(request, env) {
    const { pathname } = new URL(request.url);

    if (pathname === '/api/status') {
      // 1. まず KV から取得を試みる
      const cached = await env.STATUS_CACHE.get('all_status');
      if (cached) {
        console.log('✅ KV キャッシュヒット');
        return new Response(cached, {
          headers: { 'Content-Type': 'application/json' }
        });
      }

      // 2. キャッシュミス時のみ Firestore から取得
      console.log('⚠️ KV キャッシュミス、DB から取得');
      const data = await fetchFromFirestore(env);

      // 3. KV に保存（60秒 TTL）
      await env.STATUS_CACHE.put('all_status', JSON.stringify(data), {
        expirationTtl: 60
      });

      return new Response(JSON.stringify(data), {
        headers: { 'Content-Type': 'application/json' }
      });
    }
  }
};
```

### パターン 2: 書き込み時にキャッシュも更新

整合性を保ちながら、即座に KV も更新します。

```jsx
// 書き込み処理
if (pathname === '/api/update') {
  const body = await request.json();

  // 1. Firestore に書き込み
  await updateFirestore(env, body);

  // 2. KV キャッシュも即座に更新
  await env.STATUS_CACHE.put('all_status', JSON.stringify(body), {
    expirationTtl: 60
  });

  return new Response(JSON.stringify({ success: true }));
}
```

### パターン 3: ウォームアップ（バックグラウンド更新）

定期的に KV を更新して、常に新鮮なデータを保持します。

```jsx
// Cron Trigger で60秒ごとに実行
export default {
  async scheduled(event, env, ctx) {
    console.log('🔄 KV キャッシュを更新中...');

    // Firestore から最新データを取得
    const latestData = await fetchFromFirestore(env);

    // KV を更新
    await env.STATUS_CACHE.put('all_status', JSON.stringify(latestData), {
      expirationTtl: 120  // 念のため2分に設定
    });

    console.log('✅ KV キャッシュ更新完了');
  }
};
```

`wrangler.toml` に追加:

```toml
[triggers]
crons = ["*/1 * * * *"]  # 1分ごとに実行
```

## 📊 コスト試算例

### 前提条件

- 月間アクティブユーザー: 1,000人
- 1人あたり平均セッション: 10回/月
- 1セッションあたり平均読み取り: 20回
- **月間総読み取り回数**: 1,000 × 10 × 20 = **200,000回**

### 従来型（SDK 直通）

```
Firestore 読み取り: 200,000回
コスト: 200,000 × $0.06/100,000 = $0.12

※ 小規模だが、ユーザー増加で急増
```

### KV キャッシュ構成

```
Workers KV 読み取り: 200,000回（無料枠内）
Firestore 読み取り: 1,440回（60秒に1回 × 24時間 × 30日）
コスト: ほぼ $0.00

※ ユーザーが10倍になっても Firestore コストはほぼ変わらず
```

### スケール時（10倍成長）

|項目|従来型|KV 構成|削減率|
|---|---|---|---|
|月間読み取り|2,000,000回|2,000,000回|-|
|Firestore 読み取り|2,000,000回|1,440回|**99.9%削減**|
|コスト|$1.20|$0.00|**100%削減**|

## ⚠️ 注意点とトレードオフ

### 結果整合性の理解

Workers KV は **結果整合性** モデルです。

- 書き込み後、グローバルに反映されるまで **最大60秒**
- 同一エッジロケーションでは即座に反映されることが多い
- 地理的に離れたユーザーには遅延が発生する可能性

### 対策

1. **TTL を短くする**: `expirationTtl: 10` で10秒ごとに再取得
2. **書き込み時に KV も更新**: 即座に反映（同一エッジのみ）
3. **重要な更新は Firestore を直接確認**: トランザクション処理

### リアルタイム性が必要な場合

以下のような用途では Firestore リアルタイムリスナーを併用:

- チャット機能
- リアルタイム通知
- 在庫管理（厳密な在庫数）

## 🎓 まとめ

### Workers KV を導入すべき理由

1. ✅ **圧倒的なコスト削減**: DB 読み取りコストを 99%以上削減可能
2. ✅ **超高速レスポンス**: エッジキャッシュで〜10ms の応答
3. ✅ **高スケーラビリティ**: アクセス急増にも自動対応
4. ✅ **シンプルな実装**: 数行のコードで導入可能

### トレードオフ

- ⚠️ **結果整合性**: 最大60秒の遅延（多くの用途で許容範囲）
- ⚠️ **リアルタイム性**: 厳密なリアルタイムには不向き

### 結論

**「リアルタイム性」より「圧倒的なコスト削減」を優先する場合、Workers KV の導入は合理的な選択です。**

特に、設定情報、在席状況、ダッシュボード表示など、**10秒程度の遅延が許容できる用途**では、Workers KV を積極的に活用すべきです。
