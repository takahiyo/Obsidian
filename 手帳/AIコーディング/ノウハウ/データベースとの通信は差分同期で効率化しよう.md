# Cloud Firestore 通信コスト削減・最適化 実装覚書(改訂版)

## 1. 目的と概要

本改修の目的は、**既存のUI/UXおよび運用フローを変更することなく、Cloud Firestoreの読み取りコスト(Read Operations)を大幅に削減すること**にある。

従来の「定期ポーリング + 全件取得(Full Fetch)」型の実装は、以下の構造的な非効率を内包していた:

- データ更新頻度が低い状況でも
- 毎回同量の Read Ops を消費する

そこで本改修では、以下を組み合わせたアーキテクチャへ移行した:

- **差分同期(Incremental Sync)**
- **クライアント側の永続キャッシュ**
- **エッジキャッシュ(Cloudflare Workers + KV)**

これにより、**リアルタイム性を維持したまま、アイドル時のFirestore負荷をほぼゼロに近づける**ことを狙っている。

---

## 2. 採用したアーキテクチャ戦略

### A. 差分読み込み(Incremental Sync)

**考え方**

- クライアントは「最後にどこまで同期したか」を把握している
- サーバーには「それ以降に変更されたデータだけ」を要求する

**一般的な実装方針(参考)**

- クライアント側で「最終同期時刻(例: `lastSyncTimestamp`)」を保持
- APIリクエスト時に `since` のようなパラメータを付与
- サーバー側では `updated > since` を条件にクエリを実行

**効果**

- 更新が発生していないポーリングでは、実質的に Read Ops が発生しない
- Firestoreの課金モデルと非常に相性が良い

---

### B. ローカル永続化(Local Persistence)

**目的**

- ブラウザリロードやタブ復帰による「不要な再同期」を防ぐ

**一般的な設計**

- クライアントに以下を永続化
	- 最新のデータスナップショット(状態キャッシュ)
	- 最終同期時刻
- 初期表示はローカルキャッシュから復元
- 起動後すぐに差分同期を開始し、状態を最新化

**効果**

- UXを損なわずに通信量を削減
- ユーザー操作に起因するコストスパイクを抑制

---

### C. エッジキャッシュ(Cloudflare KV 等)の活用

**位置づけ**

- Firestoreの"前段"に配置する読み取り専用キャッシュ

**典型的な用途**

- 初回アクセス
- キャッシュ破棄後の全件取得
- 複数クライアントから同一データが要求されるケース

**効果**

- Firestoreへの直接アクセスを回避
- レイテンシ低下とコスト削減を同時に実現

---

### D. 安全なキャッシュ破棄戦略

**必要性**

- ローカルキャッシュは「ユーザーに紐づく状態」を持つ
- ログアウトやアカウント切り替え時に残存すると、重大な不整合を引き起こす

**基本方針**

- 認証状態が変わるタイミングで、ローカルおよびメモリ上のキャッシュを強制削除
- 「キャッシュが残らないこと」を安全側の設計とする

## 3. 実装観点での整理(一般化)

### クライアント側

**設定のSSOT化**

- ストレージキーや同期関連定数は一元管理
- ハードコーディングを排除し、変更耐性を向上

**同期ロジックの責務分離**

- 通信・状態管理・描画を明確に分離
- UI層は「与えられた状態を描画する」役割に限定

**キャッシュ操作の集中管理**

- 保存・復元・破棄を専用ユーティリティに集約
- 各所に `localStorage` 操作が散らばらないようにする

---

### サーバー側(Firestore + Workers 等)

**差分クエリの採用**

- `updated` などの更新時刻フィールドを基準にフィルタ
- REST API / SDK いずれでも同様の設計が可能

**キャッシュ制御**

- 読み取り: キャッシュ優先
- 書き込み: キャッシュ破棄(invalidate)

**障害検知性の向上**

- 認証情報や環境変数不足時は、曖昧に失敗させず明確にエラーを返す

---

### インフラ・環境設定

**環境変数の明示管理**

- 開発・本番で自動継承されないケースを前提に設計
- 「vars」と「secrets」を別物として扱う

**事故防止の観点**

- 「デプロイしたら動かない」原因の多くは環境変数
- 最初に確認すべきポイントとして文書化しておく価値が高い

## 5. 今後の開発・運用への提言(補強)

### 1. Firestoreの課金モデルを前提に設計する

Read Ops は「取得件数」ではなく「ドキュメント数」で課金される。差分同期は、Firestoreを使う上で最も費用対効果が高い最適化手法の一つ。

### 2. 更新時刻は"サーバー基準"で管理する

クライアント時刻は信用しない。差分同期の基準は常にサーバーが返す値を正とする。

### 3. キャッシュは"万能ではない"と理解する

書き込み頻度が高いシステムでは、キャッシュ戦略自体がボトルネックになる可能性がある。本方式は「参照頻度が高く、更新頻度が低〜中程度」のワークロードに特に有効。

### 4. 設計意図を文書として残す価値は高い

差分同期やキャッシュは「後から読むと分かりにくい」実装になりがち。本覚書のような技術背景の整理は、将来の自分・他人双方にとって保守性を大きく高める。
